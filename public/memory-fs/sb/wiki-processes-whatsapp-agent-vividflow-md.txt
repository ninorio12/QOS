# WhatsApp Agent VividFlow

## Décision

VividFlow utilise un canal WhatsApp agent séparé pour les démonstrations et échanges clients.

Canaux opérationnels VividFlow :
- WhatsApp agent : `+41 77 279 21 44`
- Email agent : `hey@vividflow.co`

Le numéro personnel de Jonathan est exclu des opérations VividFlow et ne doit pas être utilisé ni référencé comme canal agent.

## Architecture actuelle

- OpenWA self-hosted est le choix initial retenu pour les démos/pilotes, plutôt qu’un bridge Wasender fragile.
- Bridge local historique : `/home/hermes/openwa-stack/whatsapp-hermes-bridge.py`
- Service persistant historique : `whatsapp-hermes-bridge.service`
- Profil Hermes dédié : `vividflow_whatsapp_bot`
- Session dédiée : `vividflow-whatsapp-bot`
- Health bridge local historique attendu : `http://127.0.0.1:8791/health`
- Transition 2026-06-11 : Hermes dispose d’un bridge WhatsApp Baileys natif via `hermes whatsapp` + `hermes gateway`. Le spike/bridge maison ne doit pas tourner en parallèle du WhatsApp natif Hermes.

## Règles de sécurité

- Le bot WhatsApp client n’utilise pas le profil personnel `chief_of_staff`.
- Mémoire isolée : aucune donnée privée Jonathan ni contexte interne sensible.
- Toolsets sensibles désactivés par défaut.
- Contexte autorisé : offres, FAQ, process client, qualification commerciale validée.
- Escalade vers Jonathan/Thomas si le besoin sort du cadre.

## Voix du bot

- Identité : **VividFlow Assistant**.
- Ne se fait jamais passer pour Jonathan.
- Réponses très courtes : 1 à 3 phrases.
- Pas de ton consultant, pas de blabla, pas de formules creuses.
- Pas de tiret long IA.
- Voix inspirée de Jonathan : mature, directe, concrète, précise, sans enthousiasme artificiel.
- Une idée principale par message ; si c’est flou, poser une question précise.
- Préférer “on” ou “nous” quand le bot porte VividFlow, jamais un “je” qui ferait croire qu’il est Jonathan.
- Substance concrète + prochaine action ou question précise si besoin.
- Brainstorming profond activé pour idée, offre, stratégie, contenu ou décision.

## Exploitation

OpenWA passe par WhatsApp Web : c’est acceptable pour démo/interne/pilotes, mais pas une garantie production blindée.

Risques à superviser :
- déconnexion WhatsApp Web ;
- QR expiré ou à rescanner ;
- limitation Meta en cas de volume/spam ;
- session `qr_ready` nécessitant reconnexion.

Si la session du numéro VividFlow se déconnecte, générer un QR frais et demander à Jonathan de reconnecter WhatsApp Business via Appareils connectés.
## État transitoire — restriction WhatsApp

Pendant une restriction ou une période de risque WhatsApp, le bridge reste **arrêté volontairement** jusqu’à reconnexion validée.

Garde-fous préparés côté serveur :
- kill-switch activé par défaut ;
- OpenWA API maintenue healthy ;
- profil utilisé : `vividflow_whatsapp_bot` ;
- session personnelle Jonathan `jonathan-whatsapp-business` / `+41 79 309 53 58` : Hermes ne doit jamais répondre ni envoyer de message avec ce numéro ; usage autorisé uniquement pour récupérer/lister les contacts dans un espace sûr, sans action autonome ;
- session bot VividFlow `+41 77 279 21 44` : Hermes peut répondre à chaque message entrant et lancer la conversation ;
- agent externe uniquement : ne jamais divulguer d’informations sensibles, privées, internes, stratégiques, opérationnelles, techniques, credentials, contacts, clients ou backend ; répondre seulement avec des informations publiques/sûres VividFlow, sinon refuser ou escalader ;
- contact Jonathan : si quelqu’un veut réellement contacter Jonathan, donner uniquement son email professionnel `jonathan@vividflow.co` ; ne jamais donner son numéro personnel ou canal privé ;
- envoi sortant vers un contact de Jonathan : uniquement si Jonathan le demande explicitement ;
- délai humain ajouté : 8 à 25 secondes ;
- limites de réponse : max 3 réponses par contact/jour, max 8 réponses globales/jour, minimum 60 secondes entre réponses ;
- whitelist possible pour limiter le premier test à un seul numéro.

Procédure de reprise : générer un QR frais, Jonathan scanne une seule fois, retirer le kill-switch, faire un seul test entrant, arrêter immédiatement au moindre comportement anormal.

Référence anti-ban utile : `kobie3717/baileys-antiban`.
- À ne pas brancher directement dans le stack actuel sans migration : le package cible Baileys, alors que notre pilote tourne sur OpenWA.
- À reprendre immédiatement comme logique côté bridge : warmup progressif, jitter humain, plafonds par chat/global, pauses de récupération après erreur, monitoring santé session, blocage des opérations de groupe et arrêt immédiat si signal de restriction.
- Si migration OpenWA -> Baileys : auditer le package puis intégrer via `wrapSocket()` / middleware.

Note : OpenWA reste WhatsApp Web automatisé. C’est prudent pour démo/pilote, pas une garantie production. Pour client stable, préférer Cloud API/Twilio.

## Direction technique validable — migration Baileys

Le signal récent confirme que `kobie3717/baileys-antiban` est une référence utile uniquement si le stack WhatsApp migre vers Baileys. Ce n’est pas un plug-in direct pour OpenWA.

Consigne opérationnelle :
- court terme : garder OpenWA prudent pour démo/pilote, avec kill-switch, volumes bas, délais humains et plafonds stricts ;
- si besoin de stabilité supérieure : préparer une migration contrôlée vers Baileys ou vers une API officielle ;
- ne pas brancher de dépendance anti-ban sans audit code + test sandbox ;
- reprendre les patterns anti-ban comme règles de bridge, pas comme promesse de sécurité.

## Coordinateur WhatsApp — trajectoire validée

Le canal WhatsApp peut devenir un **bras droit VividFlow léger**, pas un coordinateur total sans garde-fous.

Paliers validés :
- phase 1 : 1:1 uniquement, entrants connus, bas volume, pas de groupe, pas de relance, pas de broadcast ;
- phase 2 : coordination interne légère — résumer, router, demander validation, remonter final ou blocage ;
- phase 3 : coordination client/intensive seulement via infrastructure officielle type WhatsApp Cloud API / Business Platform.

Règle groupe : éviter WhatsApp groupe + Baileys + bot coordinateur. Si test exceptionnel : réponses uniquement sur mention explicite, cooldown long, max 5–10 réponses/jour, aucun message proactif, kill-switch immédiat, test 48h entre Jonathan/Thomas uniquement. Telegram reste le cockpit coordination agents.

## Bridge natif Hermes — règle de bascule

La documentation Hermes confirme un bridge WhatsApp Baileys natif : `hermes whatsapp`, `WHATSAPP_ENABLED=true`, `WHATSAPP_MODE=bot`, `WHATSAPP_ALLOWED_USERS`. Si aucun allowed user n’est défini, Hermes bloque les entrants par sécurité.

Procédure de bascule propre :
1. arrêter/neutraliser le spike maison `node bridge.mjs` ou tout bridge OpenWA actif ;
2. activer WhatsApp uniquement sur le profil `vividflow_whatsapp_bot` ;
3. configurer whitelist, 1:1, groupes désactivés, pas de broadcast, pas d’outbound froid ;
4. pairer via `hermes whatsapp` ;
5. relancer la gateway ;
6. tester un message entrant et vérifier une seule réponse.

## Cible long terme — API officielle Meta

Pour un usage client, intensif ou vendable, la cible propre reste Meta WhatsApp Cloud API / Business Platform plutôt que Baileys/OpenWA.

Lecture opérationnelle :
- Baileys/OpenWA : acceptable pour sandbox, démo interne, bas volume et 1:1 contrôlé ;
- Meta Cloud API : préférable pour stabilité, webhooks, conformité, monitoring et scalabilité ;
- risque restant même en officiel : spam, signalements, absence de consentement ou templates refusés ;
- ordre de grandeur coût : quelques euros/mois en petit test, 10–50 €/mois en volume client modéré, plus si marketing massif.

## Persistance runtime — 2026-06-13
Sources : `raw/messages/20260613-120837_telegram-session_aeb5ff17.md`, `raw/messages/20260613-123921_telegram-session_8a9e47d4.md`.

Décision opérationnelle : le numéro agent VividFlow ne doit pas dépendre d’un démarrage manuel. Le service WhatsApp doit être traité comme runtime permanent.

État validé à conserver comme standard :
- OpenWA attaché à un service systemd persistant `openwa-stack.service`, enabled au boot ;
- bridge `whatsapp-hermes-bridge.service` enabled, actif et avec restart automatique ;
- watchdog local toutes les 2 minutes, silencieux si OK, redémarrage OpenWA/bridge si health KO ;

Point de vigilance : un service peut être online alors que WhatsApp Web/OpenWA échoue fonctionnellement avec `OpenWA send failed 500`. Pour usage client sérieux, garder Meta Cloud API / Business Platform comme cible plus solide.
