# Frontend UI Workflow

> Public/cohort-safe adaptation: this skill was sanitized from an internal delivery workflow. Replace placeholders like `<client_slug>`, `<client-dashboard-url>`, `<SECRET>` with your own environment values.

Use this skill for building, reviewing, or improving web interfaces: landing pages, dashboards, React/Next.js components, brand-aligned visual systems, UI audits, and safe design previews.

## Workflow

1. Clarify the product surface and the desired visual direction.
2. If the UI is inspired by or cloning an external SaaS, do an authenticated product-surface audit first: capture the real sidebar, toolbar, empty states, modal labels, filters, fields, settings tabs, pricing/plan limits, and creation flows before coding. Dismiss upgrade nags/interstitials (for example a post-login `Maybe Later` modal) before concluding that navigation items or surfaces are missing.
3. For an "exact / pareil / same simplicity" request, audit the *experience layer*, not just features: shell chrome, sidebar length, number of sections, visual density, CTA count, empty-state prominence, modal friction, and overall cognitive load. If your app keeps a heavier parent shell than the reference, you must call it "inspired by" rather than "same as".
4. Establish brand constraints: typography, palette, spacing, voice, forbidden motifs, and reference systems.
5. Implement with React/Next.js performance basics: avoid async waterfalls, unnecessary client state, hydration traps, oversized bundles, accidental rerenders, and remounting form field components during input.
6. Audit against web interface quality: accessibility, focus states, loading/empty/error states, forms, perceived performance, and responsive behavior. For forms/wizards, manually type multi-word text into long fields after implementation; if focus drops after every character/word, a component is probably being recreated/remounted on state updates.
7. For risky redesigns, create a non-destructive preview route/page before modifying production UI.
8. Verify visually and functionally in a browser-like workflow before claiming completion, and compare the shipped screen against saved reference screenshots of the source product when parity is claimed. For React controlled forms, use real browser input actions (`fill`, typing, clicks) during smoke tests; do not rely on `page.evaluate(() => input.value = ...; dispatchEvent(new Event('input')))` as proof, because React may not pick up synthetic DOM value assignment the same way a user action does.
9. For quick brand/UI corrections from a screenshot, treat the screenshot as the spec: identify the exact duplicated/missing element, patch only that surface, use the highest-quality existing brand asset from `public/`/assets rather than redrawing icons, and verify with a fresh browser screenshot. If the brand logo is moved into the sidebar/app rail, remove duplicate header logo marks when the requested visual shows text-only module titles. When the user asks for “exactly this sidebar”, reproduce the navigation grammar, not just colors: full width vs icon rail, brand block, non-clickable logo, divider, text labels, active-row shape, notification badges if present, bottom account card, fixed/non-scrollable behavior, and removal of unwanted logo backgrounds/wrappers. For VividFlow/Data OS sidebars, if Thomas rejects the icon-only black rail, switch to a named module rail: keep the black left surface, widen it, show module titles beside icons, and when a module has child pages, expand those pages indented directly underneath the active module (Notion-like) while preserving the top header nav/deeplink state.
10. For page/subnav bars, size the container to the actual page labels by default (`max-content` / `inline-flex`) instead of stretching a pill across available width. If the header also has right-side actions (search, notifications, profile, logout/settings), keep that action cluster statically positioned across module changes: put the nav in a flexible left group and reserve fixed/min width for the action group, then verify coordinates before/after switching modules. For premium dashboard headers, avoid oversized pills/buttons: keep the module name visible before the page nav, keep page labels compact (roughly 11–13px unless the reference clearly demands larger), and scale top-right circular action buttons/icons down before the UI reads “grossier”. For VividFlow/Data OS, if sidebar owns navigation, the header should be simple: module/page title, functional search, notification bell, compact profile/avatar, logout/settings; do not re-add duplicated page tabs. If Thomas asks for the content to move higher, the header not to be sticky/static, or the grey to match the background, use a compact `position: relative` header with matching shell background instead of a sticky blurred band. Notification bells must be stateful — no permanent orange dot and no static `+9`/count; show only unread items, open a popover, mark as seen, and clear the badge after viewing. Profile photo upload should stay available but avoid oversized crop/vertical sliders unless requested. Text inputs/textarea/editor fields should default to normal font weight (`400`), not bold. If Thomas asks to remove an “editor mode” overlay, remove every layer: script injection, public JS asset, visible library/inventory entry, and verify prod has no DOM text/script plus the asset URL returns 404. If a sticky header inside a padded dashboard shell leaves an ugly strip above it, cover the shell padding with a header `::before` pseudo-element/background rather than only shifting controls with negative margins. If a build failure shows CSS `Unclosed bracket`, search for literal `[truncated]`/ellipsis artifacts before guessing syntax; if copied tool output polluted the file, delete the corrupted lines and replace the affected selector blocks from clean source instead of appending more overrides. See `references/css-truncation-and-fit-content-nav.md` and `data-os/references/vividflow-dataos-editor-mode-header-convex-audit.md`.
11. If the reference is a standalone tool but your implementation sits inside a broader product shell, decide explicitly whether the user wants **shell parity** or **product integration** before coding. Do not assume a dedicated no-chrome route is correct just because the reference app is standalone. If the user says it must stay inside the host product (for example Data OS), preserve the host shell and only borrow the useful interaction patterns inside the content area.
10. For parity claims, verify both local and deployed builds with screenshots. A local win that is not captured again on the live route is marketing, not verification.
11. For standalone/public full-screen app surfaces inside Next.js (onboarding portals, capture tools, public forms), audit the parent shell before touching the component. If a page owns its own full-viewport design, add its route prefix to the no-chrome/full-width layout path; otherwise the global `max-w-* mx-auto px-* py-*` wrapper can create white gutters and squeeze an otherwise-correct UI.
12. After the first visual pass, sanity-check the emotional read of the screen: if it now looks like "we changed SaaS" instead of "we extended our product", you've over-copied the reference. Pull it back into the host brand by restoring native shell, primitives, typography, and color system.
12. For spreadsheet/CRM grid work, optimize the interaction model, not just the pixels: full-width grid, visible vertical separators, compact rows, low-friction `+ Nouveau` under the list, inline editing that persists, and row-click details that expose linked records (opportunities/analytics, tasks, notes, activity). If you add editable cells, verify the backend mutation path — decorative inputs are bullshit.
13. For Airtable-like CRM grids, arrows are not a substitute for drag-and-drop. Implement natural column reordering by dragging the header/handle, keep row-density controls (`Petite`/`Moyenne`/`Grande`), and ensure the table fills the available width by default with no awkward empty gutter.
14. Do not over-fit spreadsheet columns into the viewport. If the user expects an Airtable/Sheets feel, preserve useful column widths, set a real min table width, and make the grid horizontally scrollable instead of squeezing everything until it feels old-school.
15. Keep semantic CRM tabs honest: `Notes` are user-written notes linked to contacts and must include an add-note affordance; `Tasks` must include add-task affordance; completed tasks must be reversible/unchecked; system events and field-update history belong in `Logs`, not disguised as notes.
16. For contact details, a narrow right drawer is often too cramped once Tasks/Notes/Logs exist. Prefer a wider modal-drawer with dimmed backdrop, blur/overlay, strong shadow, and internal tabs (`Vue`, `Tâches`, `Notes`, `Logs`) when the contact has multiple sections.
17. For CRM leads/contact tables inspired by `All Leads` references, use a full-width dense SaaS table before inventing cards: title + compact toolbar (`Filter`, `Export`, `Import`, `New Lead`), checkbox column, sortable headers, company chips, link-styled phone/email, colored status badges, row menu, pagination. Row click should open an editable contact fiche as a modal/caption over the screen, not a cramped side panel by default; dim/blur the backdrop, stop event propagation inside the fiche, close on outside click/close/cancel/save, and verify edits update the table plus outside-click dismissal in browser QA.
18. For client/project fiches, do not hide the main work surface behind a vague new tab or header CTA. Start with an executive overview: where we are, one next action, blockers, owner, progress, and client dependencies. Separate internal project tracking from client-facing onboarding/access collection; label them explicitly (`Projet interne`, `Onboarding client`) so the user never confuses “formulaire à envoyer au client” with “pilotage livraison interne”.
18a. For Data OS client-fiche modules requested by Thomas, default to a simple rolled list of client fiches on entry — no explanatory splash or pre-opened detail. For the Data OS black left sidebar, use titled module rows (not icon-only when titles are requested) and a smooth Notion-like accordion: clicking a module opens its pages underneath, clicking the same active module again closes only the subnav while keeping the current content/page stable. Once pages live under the module in the sidebar, remove duplicate page tabs/pills from the header/module unless explicitly requested; if Thomas asks for a more sober visual, reduce orange/glow/gradients and keep the active state quiet. See `references/dataos-sidebar-accordion.md`. Row/card click opens a wide caption/modal with all onboarding/CRM fields. Put the company process workflow builder at the bottom of that fiche, not as a separate vague workspace. The builder must be meaningfully usable, not decorative/trivial: dotted canvas/grid, visible arrows/connectors, draggable nodes, `+` add step, connect mode, zoom, templates, right-side inspector, explicit save feedback, and editable node label/responsible/status/detail/icon/color/shape. Treat this as the reusable standard for every workflow surface in VividFlow/Data OS: workflows should feel closer to a lightweight Miro/system-builder than static cards. For `Équipe VividFlow → Workflows`, reuse the same builder mechanics for internal processes with internal templates and local persistence; never leave a linear sandbox when Thomas asks for the same client workflow system. If the fiche opens near a persistent sidebar/app rail, verify the workflow surface is not cut by or visually placed behind the sidebar. If the rail remains visible, position the fiche beside it with a clean gutter (`cardLeft > sidebarRight + 8`), not merely above it with z-index. Dragging must be pixel-precise and preserve the pointer grab offset; when a node is dragged near another node, provide a magnetic highlight + temporary arrow preview and auto-create the connector on release. Connector arrows must be centered relative to the actual rendered shape, not hard-coded to one card size: calculate node dimensions/centers per shape and anchor the SVG path on the shape edge along the center-to-center vector. The same board must allow manual addition of multiple independent process chains (`+ Process`), with the canvas expanding/scrolling instead of squeezing or clipping new nodes. Verify in browser: initial list has no open caption, click opens fiche with onboarding data, modal clears the sidebar, add node, add process, move/edit it, change shape/icon/name/color/status/detail, magnetic connect creates an arrow, arrows stay centered on circles/squares/triangles, save feedback appears, and reload/client switch preserves expected state when persistence is claimed. When a fiche has both onboarding/contact data and a workflow tab, QA both tabs via actual click and computed layout (`display`, `height`, `getBoundingClientRect()`), not only DOM text: legacy compact/workflow CSS or `@media (max-height:...)` rules can keep onboarding/tabs in the DOM while visually hiding them. Scope overrides to the fiche/detail class so workflow-only compact rules do not erase contact/onboarding sections. If Thomas/Jonathan asks for sections to be “modifiable”, make section titles, field labels, values, contact info, API/email/access groups, and add/delete section/field controls editable inline; for prototype persistence, scope `localStorage` by contact ID (`vividflow:data-os:onboarding:<contactId>`) and verify persistence after refresh plus contact switch. See `references/dataos-client-fiche-workflow-builder.md`, `references/dataos-workflow-canvas-drag-magnet.md`, `references/dataos-client-fiche-css-qa.md`, `references/dataos-editable-onboarding-sections.md`, and `references/vividflow-internal-workflow-builder.md`.
18b. For Data OS `Bibliothèque → Data` file-library/dropbox requests, do not leave a basic table. Build a folder-based operational surface inside the existing shell: folder grid, create/delete folders, grouped file cards, and editable title inputs. Dropbox upload, search/filter, quick folder tabs, summary counters, and explanatory empty states are optional, not mandatory; if Thomas/Jonathan calls them “bruit” or lists them for deletion, remove the entire toolbar/summary/helper block and keep only the operational folder grid + opened-folder file cards. By default keep folder interiors collapsed/hidden until a folder is clicked; if folders are derived from local file state, create a placeholder item or backend folder record so new empty folders do not vanish. Curate sources from workspace files, Hermes skills/references/media, and VPS paths when relevant; clearly distinguish a curated registry from a live filesystem index. Verify editable title inputs, create/delete folder flow, collapsed default state (`0` cards before click), absence of removed helper UI when requested, and the canonical Vercel alias after deploy. See `references/data-library-vps-hermes-dropbox.md`.

For Data OS `Bibliothèque → Projets` inventory requests (“je veux tous les projets Vercel et les repos”), replace tiny mock repo cards with an operational inventory split by source: Vercel projects and GitHub repos. Pull real accessible data first (Vercel CLI JSON pagination + GitHub API/CLI), show counts, searchable cards, URL, description/meta, and updated date. Use Thomas’ preferred wording `Projets Vercel / Github` (not `Projets Vercel + repos GitHub`) and add direct source filters (`Tout`, `Vercel`, `Repos/Github`) when both sources are present. Do not pretend the hardcoded seed list is exhaustive unless it came from a fresh inventory command. Verify DOM counts on production (`Vercel cards + GitHub cards = total`) and include representative project/repo assertions. See `references/dataos-project-inventory.md`.

For Data OS `Bibliothèque → Records` requests tied to tl;dv/R1/R2/client delivery, design it as an operational meeting library: folders such as `Clients` and `Interne`, create-folder flow, each record card showing preview, recording link, title, video sections/chapters, synthesis, and compte rendu. If tl;dv credentials are missing, do not fake a live connection: build a graceful API/fallback state, state that sync needs `TLDV_API_KEY`, and keep sample cards clearly as placeholders. Default to a cockpit board with 5 useful zones (`À cadrer`, `Build actif`, `Bloqués`, `À valider`, `Live / suivi`), keep granular stages as filter chips, and make each card expose client name, next action, owner, value, livrable progress, blocker, and target date. Add an `À traiter aujourd’hui` panel above the board for blocked/high-priority clients. For the VividFlow/Data OS `Pipeline Client` specifically, when Thomas asks to reduce/dezoom the cards, keep the React/drag structure and apply a final scoped CSS density override to `.deals-pipeline.compact-density.commercial-pipeline` so both `Leads` and `Clients` shrink together; verify card min-height/column width in browser. See `references/dataos-pipeline-card-density.md`.

Use a product-surface structure instead: title/header, toolbar with metrics/search/filter/sort, readable columns, dense deal cards, and premium drag/drop states. See `references/deals-pipeline-reference-ux.md`.

For internal client-project task tracking, optimize for flow before features: quick-add task with Enter, one required title field, progressive disclosure for owner/priority/visibility/description, template chips for recurring delivery actions, suggested next action above the list, active/done switch, and inline status/priority/visibility edits. Borrow from Plane/Focalboard/Taskcafe/Wekan, but keep it compact inside the client fiche unless drag-and-drop is truly needed. See `references/client-project-task-ux.md`.

Group rows by status (`À faire`, `En cours`, `Bloqué`, `Fait`), expose columns for task, project/client, owner, status, priority, progress, and due date, keep inline status edits, add summary/urgent panels above, and keep Kanban as a secondary view. Do not show raw technical tags as top-bar chips; group filters by meaning (`Assignation` → `Mes tâches`, `Priorité` → `Urgentes`, `Tags` → dropdown `Tous les tags`, `Historique` → `Archives`). See `references/dataos-tasks-list-ux.md` and `references/dataos-task-filter-ux.md`.
21. When a user says the page is confusing/bordel, refactor information architecture before polishing pixels: remove ambiguous buttons, reduce competing CTAs, make the default tab the overview, and expose the primary workflow in-place. A tab named `Suivi projet` is not enough if the user still cannot answer “où j’en suis ?”.
20. For operational docs/SOPs, Notion-like readability is mandatory: clear hierarchy, generous spacing, readable paragraphs, bullets, callouts when useful, and scripts/templates in distinct copy-pasteable blocks. Raw `whitespace-pre-wrap` markdown dumped into a dashboard is unacceptable; render the structure or redesign the content view.
20. For client Data OS / AIOS dashboards, do not mistake a technical foundation for a client-ready product. If the first screen leads with objects, records, views, schema versions, audit payloads, or agent API, it is DB/admin-first. A client-ready Data OS must open on an executive cockpit that answers in 10 seconds: system health, what agents did, what needs validation, what is blocked, and what business movement happened. Keep DB/schema/admin surfaces as drill-downs, not the default experience. See `references/client-dataos-v3-productization.md`.
21. For operational SOP/documentation pages, raw markdown in a `whitespace-pre-wrap` block is not acceptable. operator expects Notion-like readability: clear H1/H2/H3 hierarchy, generous spacing, short paragraphs, bullets, script/code cards labeled “copier-coller”, and a simple scan path. If the user says the mise en forme is “dégueulasse” or “toujours le problème de mise en forme”, fix the rendering layer and the source cleanup: strip repeated line-number prefixes like `1|` from Markdown before rendering, remove polluted downloadable sources too, and verify screenshots/DOM show real titles rather than raw `##` headings.
22. For client-specific Data OS dashboards shown after a sales maquette/deck, treat the maquette as the design contract.
23. For long multi-module dashboard requests, run a feature-by-feature audit loop instead of a single final glance: after each major page/surface, inspect it visually, click the relevant navigation/buttons, test the promised interaction, and only then move to the next surface. For kanban claims, drag a card between columns and verify the count/state changed; for sandbox/quick-add claims, create an item and assert its text appears. See `references/multi-module-dashboard-execution.md`.
24. For CRM-linked dashboard/contacts work, use human discernment before code polish: read every rendered word/number/CTA, remove generic SaaS filler (`Good morning`, fake `VS previous month`, unwired `Share`/`Export Data`, raw labels like `Paid At`), and connect dashboard KPIs to the contact/pipeline source of truth. Verify with `document.body.innerText`, deterministic contact search, modal label inspection, console, screenshot, and repeat on production. See `references/dashboard-crm-coherence-audit.md`.
25. For screenshot-driven dashboard/Kanban polish, treat tiny browser chrome and micro-interactions as production surfaces too: replace muddy JPG favicons with simplified SVG favicons, remove stale chart tooltip copy from the DOM, make graph points fixed if animation feels unstable, replace native selects with custom premium dropdowns when requested, make header checkboxes select every visible row, and add physical drag/drop feedback to Kanban cards. For CRM/contact pipelines, do **not** put crude `×` delete controls or tiny right-side quick-action pills (ex: repeated `Client` promotion buttons) directly on cards/table rows by default; record-level actions belong inside the opened contact fiche/modal so the table remains clean and the action is deliberate. Verify these with DOM counts/text and before/after card counts locally and on production. See `references/dashboard-kanban-polish-qa.md` and `references/crm-contact-deletion-ux.md`.
26. For premium Kanban drag states, if the user rejects a transparent/native ghost, do not keep tweaking HTML5 drag CSS or `setDragImage`. Scrap native `draggable`/`dataTransfer` and implement a Pointer Events drag layer: `pointerdown` starts, global `pointermove` updates a fixed opaque preview, `elementFromPoint` detects the target column, and `pointerup` commits the move. Verify `nativeDraggable === null`, preview opacity `1`, and source card opacity `1`. See `references/pointer-based-kanban-drag.md`.
27. For pipeline/Kanban cards in horizontally scrollable boards, implement drag auto-scroll deliberately: store last pointer coordinates, run a `requestAnimationFrame` auto-scroll loop during drag, scroll the board near left/right edges and the column stack near top/bottom edges, and disable/override `scroll-snap-type` with equal-or-higher CSS specificity because snap can silently reset programmatic `scrollLeft`. Verify by measuring `scrollLeft` during a real Playwright drag, not by code inspection. See `references/pipeline-drag-autoscroll.md`.
28. For Kanban/pipeline boards with more columns than fit onscreen, support horizontal scrolling with mouse wheel and trackpad, not just scrollbar dragging. Attach a reusable `onWheel` handler to the board container that maps dominant `deltaY` to `scrollLeft`, preserves dominant `deltaX`, and does not hijack vertical wheel while an inner column stack can still scroll. See `references/kanban-horizontal-wheel-scroll.md`.

## Product mockup realism for sales decks

When building a dashboard/Data OS mockup that will be shown as if the prospect owns it, design it as an actual product surface, not as an explanatory sales page.

- Sidebar items must navigate to distinct views or believable drill-downs; a static sidebar with dead labels feels fake.
- Replace pitch copy with product-state copy. Bad: “the cockpit Alex possesses to pilot growth.” Good: “Synthèse opérationnelle du jour”, “Sync 08:30”, “4 agents connectés”, “0 erreur critique”.
- Remove meta/maquette language from the UI: no “maquette”, “présentable R2”, “repère cité par…”, “si tout était construit…”, or “ce que cette interface permet”. Those belong in the deck narration, not inside the product.
- Use status, units, queues, filters, logs, buttons, tables, and timestamps to imply a live tool: active sync, last run, pending validations, scored leads, generated messages, connected agents.
- For mobile onboarding/wizard flows, do not simply stack the desktop sidebar, score card, and content. Use a compact mobile stepper/progress card, keep full navigation for desktop, make the primary CTA sticky at the bottom, and verify with real mobile screenshots plus `scrollWidth === innerWidth` at 360–390px.
- For public client onboarding, hide implementation mechanics from the client. The shareable URL should be simple (`/onboarding`), create/generate the tokenized session silently, then redirect internally. Never make the client type or understand a token; tokens are plumbing, not UX.
- For Client Delivery client onboarding/access forms, use invitation-first collection: security/RGPD frame upfront, ask users to invite `<contact-email>`, never request passwords in the form, and include “I’ll do it later / I don’t know how” fallbacks for technical steps. Use `votre agent IA` in public copy, not `Hermes`. Keep the “tools/access” chooser simple (CRM, cloud/documents, Meta BM, autre) and move mandatory technical accounts/API keys (Browser Use, Gemini/Google AI Studio, Fal AI, Firecrawl, Vercel, Hostinger/VPS) into a separate required “Comptes & API” step. See `references/client-onboarding-access-ux.md`.
- For VividFlow/Kalvi-inspired onboarding, do not default to a dark SaaS wizard with benefit cards, 3D icons, and static recommendations. If Jonathan references Kalvi/Boost IA captures, the desired grammar is a light canvas/system-builder: grid, blocks, arrows, modules that appear progressively, and a final plan generated from answers. Keep sector copy generalist by default and use brand color as restrained accent rather than full visual mood. See `vividflow-agaas-product/references/vividflow-onboarding-kalvi-style-direction.md` for the product doctrine.
- Place help/tutorial videos at the point of friction inside the form, not in a separate help page nobody reads: access-invitation tutorial in the tools step, API account tutorials in the Comptes & API step, Drive/resource tutorial in resources, human-validation examples in validation.
- After visual QA, scan copy specifically for explanatory phrases and convert them into UI labels, states, or actions.
- Avoid custom cursors on serious client-facing onboarding/forms unless the user explicitly asks for one. operator found the custom pointer unpleasant after testing; default browser cursors are usually the better UX for forms. If a custom cursor already exists and the user reports discomfort, remove the feature entirely: delete the cursor DOM/SVG, `cursor: none` rules, global `html/body` cursor-hiding classes, mousemove handlers, refs, and animation frame loop, then verify the live bundle no longer contains the custom cursor markers. If a custom cursor is explicitly requested on a desktop-only surface, treat it as interaction engineering, not decoration: use `@media (pointer: fine)`, hide the native cursor across the whole surface and descendants with `cursor: none !important`, and use `requestAnimationFrame` interpolation. Prefer updating a cursor DOM ref's `transform` directly over setting React state every mouse frame; React state can cause pointless rerenders on already-heavy onboarding forms. See `references/custom-cursor-premium-surfaces.md`.

## Pitfalls

- **Framer project links are not public editing access**: `<url> usually redirects to `/login` unless the agent's browser already has an authenticated Framer session. Before promising direct edits, probe the URL with redirects and check for `framer.com/login`. If redirected, ask for an invite to `<contact-email>` and an accepted/login-ready browser session; otherwise work from the public site URL for audit/copy/structure while access is being fixed. Never ask for passwords in chat.
- **Framer public site audit first**: when the user shares the public domain while editor access is blocked, still capture/inspect the live site (HTML text, meta tags, desktop/mobile screenshots) and deliver actionable copy/IA/design recommendations. Don't stall the work just because the editor is gated.

- **Custom cursor native cursor leak**: `md:cursor-none` on the page wrapper is not enough. Buttons, inputs, textareas, selects, labels, and utility classes like `cursor-pointer`/`cursor-text` can resurrect the browser cursor on hover. Add a scoped rule like `@media (pointer: fine) { .surface, .surface * { cursor: none !important; } }`, keep the custom cursor `pointer-events-none`, and verify over buttons + form fields. But for onboarding/forms, first ask whether a custom cursor is worth it at all; operator disliked it in practice, so the safe default is native cursor, not premium gimmick.
- **Auth/profile header semantics**: if the user wants profile settings from the avatar, wire the avatar button to the profile/settings surface and replace a generic settings/sliders button with an explicit `Se déconnecter`/logout action. Do not introduce `useClerk()` into a component unless the rendered tree is definitely wrapped in `<ClerkProvider>` in every environment; otherwise use the app’s existing auth boundary or a safe logout fallback and verify the page does not 500 locally/SSR.
- **Truncated source corruption**: if `next build` reports CSS `Unclosed bracket` and the source includes literal `[truncated]`, `.... [truncated]`, or ellipsis copied from tool output, stop treating it as a design/CSS issue. Remove every corrupted line, rewrite the affected selector blocks from complete source, then run build/typecheck/tests and browser QA. Appending overrides while the corrupted line remains will still fail PostCSS. See `references/css-truncation-and-fit-content-nav.md`.
- **Oversized or jumping page nav/header bars**: when a subnav has only a few labels but spans the whole header, the bug is layout semantics, not polish. Use `max-content`/`inline-flex`; when modules have different page counts, keep the right-side tools in a fixed/min-width action cluster so search/notification/profile/logout buttons do not jump between modules. Keep the active module label before the page bar when the user asks for context, and prefer compact proportions over dramatic pills: a page nav that visually dominates the dashboard makes the product feel crude. Verify with browser coordinates, not eyesight only.
- **Overloaded icon rail/sidebar**: if the user says the sidebar is “trop chargé”, do not add more glow, labels, gradients, or larger active states. Simplify first: narrow the rail, reduce logo/button/icon sizes, increase vertical breathing room, lower glow opacity, and keep the active indicator subtle. Premium black rails should feel quiet and precise, not gamified.
- **Task filter chip soup**: if a Tasks page shows `Mon`, `Urgent`, client slugs, build-stage tags, and `Archives` as one flat chip row, it leaks backend taxonomy into the UX. Replace it with semantic groups and hide tags in a dropdown. Text/DOM checks can still include option values from a native `<select>`; use screenshot/vision QA to confirm those values are not visible as chips. See `references/dataos-task-filter-ux.md`.
- **Delivery board column squeeze**: if a client Delivery pipe looks “tassé” or labels/cards are unreadable, do not just shrink fonts or tweak colors. The product problem is information architecture: collapse detailed lifecycle stages into 5 executive zones, expose detailed stages as filters, use horizontal scroll intentionally, and verify a screenshot at desktop width. A partially clipped right-side column is acceptable only if the scroll affordance is obvious; otherwise reduce column width/count or add a fade/scroll hint.
- **Redundant module intros on operational boards**: if the shell/subnav already names the module and page, repeating the same title/subtitle inside the page makes the product feel amateur and verbose. Remove explanatory hero copy and let the work surface carry the hierarchy. For deals/leads pipelines, follow `references/deals-pipeline-reference-ux.md` and verify the old repeated text is absent from the rendered DOM.
- **React form focus loss**: if typing in a textarea/input causes the field to deselect on each keystroke, look for components defined inside the parent render, render-prop factories returning new component identities, or changing `key` props derived from field values. Hoist field components outside the render path, memoize only where identity matters, keep stable keys, then verify by typing a multi-word sentence in a long field. This bug is not “UX polish”; it makes onboarding forms unusable.
- **Sequential onboarding wizard**: when the client-facing flow must be completed step-by-step, do not expose clickable tabs/sidebar navigation. Show progress, keep `Retour` + `Sauvegarder et continuer`, and make skipping impossible in the default UX. Help videos belong inline at the exact friction point, not buried elsewhere.
- For route-shell bugs, don't redesign the component first. Inspect `app/client-layout.tsx`, root layout/body classes, route prefix lists, and wrapper max-width/padding. A full-screen page wrapped by `max-w-4xl mx-auto px-4 py-8` will look broken in production even if the page component is fine.
- `min-h-screen`/`min-h-dvh` inside a constrained parent is not enough; the parent layout must allow full viewport ownership. For loading/error states on public portals, `fixed inset-0` is a useful defensive pattern.
- For marketing/landing pages, especially mobile-first sales pages, verify the *true CSS viewport* before trusting screenshots. Headless `google-chrome --window-size=390,... --screenshot` can still render with a wider CSS viewport or inconsistent device assumptions; use Playwright/device emulation or Chrome DevTools Protocol `Emulation.setDeviceMetricsOverride({ width: 390, mobile: true })`, then evaluate `document.documentElement.scrollWidth <= innerWidth` and list overflowing offenders. A screenshot that looks clipped under the wrong viewport is not evidence; DOM metrics under real mobile emulation are.
- For filmable architecture diagrams / schema canvases, visual legibility beats “everything visible at once.” If feedback says “pâté”, “collé”, or “ça s’entrelace”, increase canvas size and whitespace, separate layers vertically, route arrows with fewer diagonals, move labels away from connectors, use default zoom-out/fit, and screenshot-QA for cropped nodes/overlaps before shipping.
- When a user calls a design "too pastel", "too simple", or "template/Webflow-like", do not just darken colors. Increase design maturity: stronger typography, sharper contrast, a distinctive product/mechanism visual, restrained motion, fewer generic card grids, and mobile-first composition.
- Do not mix preview experiments into production routes without explicit rollout intent.
- Never claim UI completion without checking actual rendered behavior where possible. If live screenshot tooling hangs, label any generated/mock preview as representative, not as captured live UI, and still verify the live deployment with HTTP/DOM/status checks.
- When the user asks for a quick visual/"visu" of a local Next.js dashboard, prefer real screenshots over explanation: locate existing screenshots first, then run/verify the app locally, capture 2-4 key routes with headless Chrome, and send the image files directly. If Next reports an existing dev server that hangs, verify the PID belongs to this project, terminate only that app process, remove stale `.next/dev/lock`, restart on a non-conflicting port, and confirm with `curl` before screenshotting. If local `next dev` returns 500 with missing `.next/routes-manifest.json` or `.next/server/pages-manifest.json` after a build/dev mix, kill that project’s dev process, `rm -rf .next`, restart dev, wait for readiness, and verify HTTP 200 before browser QA.
- If a rendered preview is using fallback/mock data because a live backend (Convex, API, DB) is unavailable, disclose it plainly next to the images. Pretty pixels with dead data are useful, but pretending they are live is how dashboards become theater.
- For Framer direct-editing requests, distinguish three states: project URL received, invitation accepted, and agent browser session authenticated. A Framer project URL can still redirect to `/login/` after invitation acceptance, and headless email login may fail with `Verification Failed — We couldn’t verify that you’re human`. Verify access with a real redirect/screenshot check before promising edits; if blocked, ask for a one-time magic link/code, never a password, and keep working on public-site copy/layout in parallel. See `references/framer-direct-editing-access.md`.
- For external SaaS clone requests ("exactement pareil"), never trust dump filenames or DOM text alone. First prove authenticated app access with screenshots; if blocked by login/email confirmation/paywall, state that the result is only “inspired by / Fructu-like” until a full gap audit is completed.
- After login, watch for blocking onboarding or upgrade modals before auditing the app shell. If you don’t dismiss them, you’ll map the popup instead of the product and miss sidebar/routes that are actually there.
- For "same simplicity / same intuitiveness" requests, feature parity is not enough. Compare the rendered app shell against the reference for navigation breadth, chrome weight, number of competing actions, modal friction, and empty-space ratio before claiming success.
- If the implementation lives inside a broader product shell than the reference app, do not blindly strip the shell. First determine whether the user wants a standalone-feeling clone or a native module inside the host product. "It should integrate into Data OS" means keep the host shell and brand; cloning the external shell will make it feel like you changed SaaS.
- When simplifying a module inspired by another SaaS, remove obvious foreign-product artifacts first: affiliate cards, pricing/free-plan blocks, upgrade nags, and other marketing chrome that make the page read like a different product.
- For CRM/spreadsheet surfaces, centered max-width cards, rounded wrappers, and side gutters fight the table metaphor. Use the full content width, square edges, compact rows, and both horizontal and vertical grid lines.
- Do not implement “inline editing” as uncontrolled UI only. Add/verify the mutation path, handle blur/Enter/Escape, and stop row-click propagation from inputs/selects so editing doesn’t accidentally open the detail drawer.
- Do not treat Contacts, Analytics, Tasks, and Notes as unrelated tabs. In CRM UX, the contact is the anchor object; analytics/activity, tasks, notes, and opportunities/deals must be reachable from the contact details.
